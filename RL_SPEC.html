Leaper RL Specification

A single-source technical reference for everything RL-specific about the Leaper: sensors, action space, the underlying model, and the environment/experiment design. All numbers are pulled directly from rl_environment.py, train_rl.py, and a loaded PPO_12 policy. Reflects the current PPO_11/PPO_12 baseline.

One framing note up front. The Leaper RL agent lives in a lightweight simulated 2D world, not on physical hardware. There are no real hardware sensors (no cameras, no IMU, no encoders). Every "sensor" below is a value the simulator computes from the known world state each step and hands to the policy as part of its observation vector. Where a value has a natural physical location on the body, that is given.

1.Sensors (observation channels)

The policy receives an 18-value observation every step, all float32. It splits into two groups: 10 navigation/proprioception values (indices 0–9) and 8 rangefinder values (indices 10–17). One reading is produced per environment step (sampling rate = control rate = 1 per step, 400 steps max per episode). Source: LeaperReachEnv._observation and _ray_distances.

Obstacle-clearance rangefinders (indices 10–17) — "the eyes"

Eight rays cast from the body center, fanning out every 45° around the current facing. Ray 0 points straight ahead; the other seven are spaced 45° apart around the full circle.

  • Type: analytic ray-cast (ray–circle and ray–wall intersection), not a physical LIDAR. Computed in _ray_distances.
  • Measures: clear distance along each ray to the nearest of the five obstacles or the four arena walls.
  • Range / normalization: RAY_MAX_RANGE = 12.0 units. Output = clear distance ÷ 12.0, clipped to [0,1]. 1.0 = nothing within 12 units; near 0 = an obstacle/wall right against that ray.
  • Sampling rate: once per step.
  • Output format: 8 × float32 in [0,1].

Adding these eight rays (PPO_11) is the single change that took the project from 5% to 69% deterministic success — the policy went from blind to sighted.

Collision-sensing geometry (used internally, not a numeric channel)

Collisions are tested against 19 sample points on the body (_collision_points):

  • 1 body point at the center, collision radius AGENT_RADIUS = 0.75.
  • 18 leg points: the hexapod's 6 legs at fixed body-frame angles LEG_ANGLES = (±0.62, ±1.57, ±2.42) rad. Each leg has 3 samples along its length at radii 1.2, 2.2, 3.24 units from center, each with collision radius 0.24.

A pose "collides" if any of the 19 points crosses a wall or an obstacle circle. This drives the last_collision flag (index 7) and the collision penalty, but the geometry itself is not fed to the policy as numbers.

2.Capabilities / Action space

The action space is a 2-value continuous Box, each in [-1, 1], float32. One action is applied per step; values outside [-1,1] are clipped.

ActionRangeMeaningConstraint (per step)
action[0] — throttle[-1,1]Signed forward/back. +1 = full forward, 0 = stop, -1 = full reverseMax displacement MOVE_SPEED = 0.75 units/step
action[1] — turn[-1,1]Turn rate, either directionMax rotation TURN_SPEED = 18°/step

Behaviors supported: move forward, move backward (reverse), turn left, turn right, stop, and any blend (arc = throttle + turn together). The robot moves along its facing direction; there is no strafing and no jump — despite the name "Leaper," the RL agent is a planar navigator with no vertical axis.

Collision-response rule (PPO_12). Each step computes a candidate turn, then a candidate move along the new facing:

  • If the full combined turn-and-move pose is collision-free → apply both.
  • If blocked → resolve independently: rotate in place if the turned pose alone is clear, then translate along the resolved facing if that alone is clear.

This lets a robot touching an obstacle still turn or reverse out of contact instead of freezing. The collision flag and its penalty still reflect the full intended move, so a robot sliding along an obstacle edge while still progressing registers a collision every step (a known quirk that inflates the reported collision rate).

3.Underlying AI model

Confirmed by loading the trained PPO_12 policy (ppo_12_collision_recovery_100k/leaper_ppo.zip).

  • Algorithm: PPO (Proximal Policy Optimization), Stable-Baselines3.
  • Policy class: MlpPolicy → ActorCriticPolicy (separate actor and critic networks; no shared trunk, no CNN, no RNN — flat 18-vector input).
  • Total parameters: 10,949 (all trainable).
  • Activation: Tanh throughout.
  • Action distribution: diagonal Gaussian — action_net outputs the 2 means; a separate state-independent log-std vector (2 params) sets exploration spread.

4.Environment & experiment design

4.1 Environment (LeaperReachEnv, a Gymnasium gym.Env)

  • World: continuous 2D plane (X, Z), bounds [-25, 25] on both axes.
  • Target: fixed at (18, 18), radius 1.4. Reached when distance ≤ 1.4 + 0.75 = 2.15.
  • Obstacles: 5 fixed circles (x, z, radius): (-10,-5,3.2), (1,4,3.0), (10,11,2.8), (-7,13,2.6), (12,-8,3.4).
  • Spawn (per episode): random position in [-21, 21]² with random yaw in [-π, π], re-sampled until collision-free and ≥ 2 units clear of the target. Starts and headings randomized every episode; arena, obstacles, and goal fixed.
  • Episode length: up to 400 steps.
  • Observation space: Box(-1, 1, shape=(18,), float32) — see §1.
  • Action space: Box(-1, 1, shape=(2,), float32) — see §2.

4.2 Reward structure (per step)

reward = progress + time + collision + goal

progress   = 0.2 * (prev_distance - current_distance)   # DISTANCE_REWARD_SCALE
time       = -0.01                                       # every step
collision  = -0.18 if the intended move was blocked else 0
goal       = +25.0 on the step the target is reached else 0

The only extra reward state is prev_distance, reset at episode start and updated each step. Progress reward is symmetric: closer is positive, away is negative. No other shaping terms.

4.3 Termination / truncation

  • Terminated (success): distance ≤ 2.15 → +25 and episode ends.
  • Truncated (timeout): step count reaches 400.
  • Collisions never end an episode — they only cost reward and block motion (why a stuck deterministic policy can loop to timeout, the failure PPO_12 addressed).

4.5 Evaluation setup

Two distinct measurements, kept separate on purpose:

  • Periodic checkpoint eval — every 10,000 steps: 25 deterministic episodes (seeds 10,000 + i) plus 5 exploratory episodes (seeds 20,000 + i) recorded for the visualizer, and a checkpoint model saved.
  • Final deterministic diagnostics — after training, 100 deterministic episodes on fixed seeds from 10,000. This is the canonical "exam" all runs are compared on: success rate, timeout rate, mean reward, net target progress, forward/reverse/stopped %, throttle stats, collision-step %, mean & worst collision streak, average episode length, and reward breakdown.

Fixed evaluation seeds are held constant across runs so cross-run comparison stays fair, even though training now uses natural random seeds. The latest 100 stochastic training episodes are also summarized separately and are not treated as evidence of deployment quality.

4.6 Experiment discipline

  • One controlled change per run. Change exactly one learning-relevant thing (observation, action, physics, or reward) per experiment; record it in TRAINING.md. Any such change invalidates older trained policies.
  • Smoke first, then main. A 20k-step smoke test (collects 24,576) verifies the run is NaN-free and passes Gymnasium's check_env before the full run.
  • Scale up only after replication. Increase total timesteps only once a change repeats across seeds and success/progress is still improving.
  • Artifacts are per-run and git-ignored. Each run writes to its own --artifact-dir (model, checkpoints, CSVs, TensorBoard events, replay JSON, evaluation and config JSON).
